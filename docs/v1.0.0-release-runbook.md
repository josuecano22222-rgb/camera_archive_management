# Camera Archive Management V1.0.0 — gated release runbook

**Status:** preparation only. The current workspace changes are not yet committed, validated on a Frappe v15 Bench, or approved for production. Do not execute the production section until all staging gates pass, an immutable release commit is published, the production backup is verified, and the operator explicitly authorizes the maintenance window. Run exactly one numbered step, verify its stated result, and stop for operator confirmation before continuing.

## Non-negotiable safeguards

- Never install demo records during app installation or migration. Demo generation is a separate, explicit action on a disposable, non-production site only.
- Do not set `camera_archive_allow_demo_data=true` on `frappe.com`.
- Preserve Siraj settings and data, especially `siraj_research`, and do not delete, empty, move, or replace `sites/frappe.com/private/siraj_tile_cache/`.
- Keep external tile fetching and shared-cache writes disabled until post-release checks have passed and the administrator explicitly enables them.
- Do not use `bench clear-cache`, Redis flushes, or tile-cache deletion as a substitute for a targeted release check. None of the app's release steps requires erasing the Siraj tile cache.
- Stop on any unexpected branch/commit, migration warning, failed check, missing backup, or data discrepancy. Do not skip a gate to meet a maintenance-window deadline.

## Release values to pin before operating

Record these values in the change ticket before starting. Do not substitute a moving branch name for the release commit during production rollout.

```text
BENCH=~/frappe-bench
PRODUCTION_SITE=frappe.com
STAGING_SITE=<restored-disposable-test-site>
RELEASE_BRANCH=arena/8970c81a-camera-archive-management
RELEASE_COMMIT=<full-reviewed-commit-sha>
```

The release commit is intentionally a placeholder until the V1.0.0 changes have completed review and been committed. Production currently remains on its previously deployed commit; this runbook does not deploy anything by itself.

## Staging: update, migrate, test, and build

### 1. Create or refresh a disposable staging copy

Use the approved, encrypted production backup and restore it only to a separate disposable site. Follow the Bench's documented restore procedure for the database and both public and private files. Never restore over `frappe.com`. Confirm that the resulting `STAGING_SITE` is not the production site and that credentials, outbound integrations, scheduled jobs, and any real camera endpoints are disabled or safely isolated.

**Gate:** confirm the disposable site's name and isolation before proceeding.

### 2. Update the staging app to the reviewed release commit

From the Bench root, first verify the target and app checkout. Substitute only the pinned values above:

```bash
cd ~/frappe-bench
git -C apps/camera_archive_management status --short --branch
git -C apps/camera_archive_management fetch origin arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management checkout arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management pull --ff-only origin arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management rev-parse HEAD
```

Compare the final line to `RELEASE_COMMIT`. Stop if there are local changes or the hashes differ; do not discard unknown changes.

**Gate:** operator confirms the app is at the exact reviewed commit.

### 3. Run staging migration

```bash
cd ~/frappe-bench
bench --site <restored-disposable-test-site> migrate
```

Review the complete output and logs. Specifically verify that the legacy Camera Photo gallery migration preserves every image, caption, description, primary selection, and File attachment; verify that no Siraj-owned DocType or cache data was changed. A migration exception or any mismatch is a stop condition; restore staging and investigate rather than retrying blindly.

**Gate:** operator confirms migration completed cleanly and the data comparison is acceptable.

### 4. Run the full app test suite on staging

```bash
cd ~/frappe-bench
bench --site <restored-disposable-test-site> run-tests --app camera_archive_management
```

Check the exit code and complete test report. Include the Camera gallery no-cap regression (51 images), permissions, map APIs, and patch/migration tests. Also run any site-specific integration tests required by the change ticket.

**Gate:** all required tests pass; record the test output/artifact before continuing.

### 5. Build staging assets

```bash
cd ~/frappe-bench
bench build --app camera_archive_management
```

Check the process exit code and build output. Do not continue after asset warnings/errors that have not been understood and resolved.

**Gate:** successful build recorded.

### 6. Staging smoke test and release decision

In the staging UI, verify camera list/form/gallery behavior (including more than 50 photos), primary image, map layers and filters, replay, measurements, permissions, country outlines and local lookup, and both languages. Compare legacy image files and metadata before/after migration. Confirm no fictional records were created by installation/migration. Check that tile fetching/shared-cache writes remain off by default and that the existing Siraj tile cache remains intact.

Optional synthetic demo validation must use only the disposable staging site, only after explicitly enabling its per-site flag, and must create/delete only the tagged `CAM-MAP-V1-DEMO` records. Return the flag to disabled afterward.

**Gate:** release owner signs off on staging evidence and authorizes scheduling a production window. Otherwise stop here; production steps are not authorized.

## Production: separately authorized maintenance window only

Do not begin unless staging gates have passed, the immutable release commit is published, a full backup is complete and verified, a rollback plan is tested, and the system owner explicitly authorizes this exact production maintenance window. The operator must perform one numbered step and confirm its result before starting the next.

### 7. Take and verify a fresh full production backup

```bash
cd ~/frappe-bench
bench --site frappe.com backup --with-files
ls -lt sites/frappe.com/private/backups | head -20
```

Verify that the new database, public-files, and private-files backup artifacts exist, are non-empty, have been copied to the approved protected/off-site storage, and are restorable. Record names, sizes, timestamps, and checksums in the change ticket. Do not continue with a partial backup.

**Gate:** owner confirms a complete, verified backup and the active maintenance-window authorization.

### 8. Enable maintenance mode

```bash
cd ~/frappe-bench
bench --site frappe.com set-maintenance-mode on
```

Verify the site is in maintenance mode and user-facing downtime has begun as scheduled.

**Gate:** operator confirms maintenance mode is active.

### 9. Update production code to the exact approved release

First confirm the checkout is clean and on the expected branch, then fetch and fast-forward only to the release branch. Keep the release ticket's full commit hash at hand:

```bash
cd ~/frappe-bench
git -C apps/camera_archive_management status --short --branch
git -C apps/camera_archive_management fetch origin arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management checkout arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management pull --ff-only origin arena/8970c81a-camera-archive-management
git -C apps/camera_archive_management rev-parse HEAD
```

Compare the final hash exactly with `RELEASE_COMMIT`. If it differs, stop and roll back according to the approved plan; do not migrate an unapproved revision.

**Gate:** owner confirms the production code matches the pinned commit.

### 10. Build production assets

```bash
cd ~/frappe-bench
bench build --app camera_archive_management
```

**Gate:** successful build with no unresolved errors.

### 11. Migrate production

```bash
cd ~/frappe-bench
bench --site frappe.com migrate
```

Review all output and logs. Do not run demo generation. Do not remove or clear `sites/frappe.com/private/siraj_tile_cache/`. Stop immediately on warnings, migration failures, unexpected DocType ownership, lost gallery data, or any discrepancy; follow the rollback plan while maintenance mode remains on.

**Gate:** owner confirms migration and the expected data/schema checks completed cleanly.

### 12. Restart and perform production smoke checks

```bash
cd ~/frappe-bench
bench restart
```

With maintenance mode still on, verify application health, login as the authorized operator, key list/form/map workflows, gallery images, permissions, logs, Siraj settings and `siraj_research`, and the unchanged private tile-cache directory. Confirm tile fetching/shared-cache writes are still disabled.

**Gate:** owner explicitly approves taking the site out of maintenance mode.

### 13. Reopen service and monitor

```bash
cd ~/frappe-bench
bench --site frappe.com set-maintenance-mode off
```

Monitor application/error logs and user-facing behavior for the agreed observation period. Do not enable tile fetching or shared-cache writes during this release step. If checks fail, re-enable maintenance mode and follow the approved rollback procedure; do not improvise a destructive cache cleanup.

**Gate:** close the change only after monitoring is clean and the owner records acceptance.
